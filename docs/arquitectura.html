Qué hace cada servicio

Render

Donde vive la app
  • Ejecuta el servidor y entrega las pantallas.
  • Construye la app con el Dockerfile desde GitHub, rama main.
  • Tras subir cambios: Manual Deploy → Deploy latest commit.
  • No guarda archivos de forma permanente: por eso los datos van en Neon.

Neon

La base de datos (PostgreSQL)
  • La única base de la app publicada: 21 tablas con usuarios, salud, comidas, rutinas, series y récords, rangos, lesiones, equipos, mensajes, tickets y fotos.
  • Está aparte de Render: los datos sobreviven a reinicios y deploys.
  • Las contraseñas se guardan cifradas (bcrypt), nunca en texto.
  • En Tables se ve cada tabla con sus filas.

GitHub

El código y su historial
  • Cada cambio queda guardado con su explicación.
  • El CI pasa los 450 tests y construye la imagen de Docker en cada subida.
  • Cada mañana una tarea programada envía el recordatorio al celular.

SonarQube Cloud

Calidad del código Passed · todo en A
  • Analiza solo cada cambio: fallos probables, seguridad y mantenibilidad.
  • 0 bugs, 0 vulnerabilidades, 0 code smells.

Brevo

Envío de correos
  • Bienvenida, recuperar contraseña y alertas de salud y carga.
  • Plan gratis: 300 correos al día.

Google Cloud

Entrar con Google
  • Solo pide nombre y correo; no accede a nada más de la cuenta.
  • Requiere la página de privacidad publicada en la app.

Claude

Asistente IA “Vita” Sin activar · modo básico gratis
  • Con una clave de pago conversaría usando los datos del atleta.
  • Sin clave responde con los análisis propios de la app.

La configuración secreta

Vive en Render, en el grupo de variables Pro. El código nunca lleva estos valores; solo sus nombres.

VariableQué guarda
DATABASE_URLDirección y contraseña de la base de Neon
JWT_SECRETClave con la que se firman las sesiones
ADMIN_PASSWORDContraseña del admin al crear la base por primera vez
DATOS_DEMOfalse: no crear cuentas de prueba
BREVO_API_KEY · CORREO_REMITENTEEnviar correos con Brevo
GOOGLE_CLIENT_IDBotón “Entrar con Google” (este no es secreto)

Cómo llega un cambio a la web

  1. Se cambia el código y se prueba en el computador, con la base local.
  2. Se sube a GitHub (rama main). El CI pasa los tests y SonarQube analiza.
  3. Manual Deploy en Render. Render construye la imagen con Docker y publica la nueva versión.
  4. Neon no se toca. Los usuarios y sus datos siguen ahí.

Guion para la demo

  1. La app. Portada y registro. Con un atleta: "Hoy te toca…", series y récord, Mis rangos y Vita. Con el médico: registrar una lesión. Con el admin: Equipos. Y cómo se instala en el celular.
  2. Render. El servicio en línea, el historial de deploys y los Logs (“Base de datos lista · postgresql”).
  3. Neon. Tables → usuarios o salud: los datos que se acaban de ver en la app. Las contraseñas aparecen cifradas.
  4. GitHub. El historial de cambios y Actions con el CI en verde.
  5. SonarQube. Quality Gate Passed y las notas en A.

Cuidado al proyectar

  • No muestres la connection string de Neon ni las variables de Render con su valor visible: dan acceso a todos los datos.
  • En Neon, enseña las tablas sin abrir datos personales de usuarios reales, o muéstralos rápido.
  • No dejes la sesión de Render o Neon abierta en un computador de la universidad.
